# Spring Boot로 재고와 결제 정합성 다루기: 조건부 UPDATE부터 Outbox까지

재고가 한 개 남았을 때 두 사람이 동시에 주문하면 어떻게 될까. 재고 조회와 차감을 트랜잭션으로 묶으면 괜찮을 것 같았다. 그런데 두 요청이 모두 수량 1을 읽는다면 주문은 두 개가 만들어질 수 있다.

재고를 조건부 UPDATE로 차감하면서 이 문제는 해결했다. 그다음에는 결제가 걸렸다. 결제사에는 승인이 끝났는데 우리 서버가 응답을 받지 못했다면, 실패로 처리하고 재고를 돌려줘도 될까?

이 질문을 따라 Java와 Spring Boot, JPA로 주문·결제 실습 프로젝트를 만들었다. 주문 생성에서 시작해 예약 만료, 결과 재조회, 환불, Outbox와 Kafka까지 붙였다. 이 글에는 코드를 추가할 때마다 어떤 실패 상황을 다뤘는지 정리했다.

## 먼저 정한 주문 정책

초기 데이터는 이벤트 하나, 재고 100개, 가격 10,000원이다. 주문을 만들 때 재고 한 개를 예약하고 10분 안에 결제 결과를 반영하면 주문을 확정한다. 기한이 끝나면 예약을 풀고, 그 뒤 승인 사실을 확인하면 환불한다.

여기서 기한은 서버가 결제 성공을 반영하는 시각을 기준으로 판단했다. 결제사의 승인 시각을 기준으로 삼지는 않았다. 이 차이를 정하지 않으면 결제 응답이 늦었을 때 같은 주문을 두고도 처리 결과가 달라진다.

같은 사용자는 같은 이벤트에 한 번만 주문하도록 제한했다. 취소나 만료 뒤 다시 주문하는 경우도 허용하지 않는 학습 정책이다.

구현에는 Java 21, Spring Boot 4.1.1, Spring Data JPA, Gradle, Flyway를 사용했다. 기본 DB는 H2다. 실제 결제사 대신 승인·실패·타임아웃을 재현하는 가짜 결제사를 만들었고, 메시지 전달은 로컬 방식과 Kafka를 선택할 수 있게 했다.

## 조회한 수량을 믿지 않고, 변경할 때 재고를 확인했다

재고를 조회하고 수량이 남아 있으면 엔티티 값을 하나 줄이는 방식에는 아래와 같은 실행 순서가 가능하다.

```text
요청 A: 재고 1개 조회
요청 B: 재고 1개 조회
요청 A: 주문 생성, 재고를 0으로 저장
요청 B: 주문 생성, 재고를 0으로 저장
```

재고는 음수가 아니어도 이미 한 개를 초과 판매했다. `@Transactional`은 이 조회·수정 흐름을 자동으로 직렬화하지 않는다. 함께 롤백할 변경을 묶는 것과 다른 요청의 동시 접근을 제어하는 것은 각각 처리해야 한다.

재고 차감은 아래 JPQL로 바꿨다.

```java
@Modifying
@Query("""
    update Inventory i
    set i.available = i.available - 1
    where i.eventId = :eventId
      and i.available > 0
    """)
int decreaseIfAvailable(@Param("eventId") Long eventId);
```

수량 확인과 차감이 하나의 UPDATE에서 실행된다. 호출부에서는 변경된 행 수를 검사한다.

```java
int updated = inventoryRepository.decreaseIfAvailable(eventId);
if (updated != 1) {
    throw new IllegalStateException("재고를 예약할 수 없습니다.");
}
```

`eventId`가 기본 키이므로 변경할 수 있는 행은 최대 한 개다. 성공은 1이고 재고가 없거나 대상 행이 없으면 0이다. `updated > 1`만 검사하면 차감에 실패한 경우를 놓친다.

주문 저장과 재고 차감은 같은 트랜잭션으로 묶었다. 현재 구현은 주문을 먼저 저장한 뒤 재고를 차감한다. 차감에 실패하면 런타임 예외로 주문 저장까지 롤백한다. 뒤에서 결제 시도나 Outbox 저장에 실패해도 이 트랜잭션의 변경은 함께 롤백된다.

중복 주문은 별도로 막았다. 주문 테이블의 `UNIQUE(user_id, event_id)` 제약으로 같은 사용자의 같은 이벤트 주문 두 개가 커밋되지 않게 했다. 사전 조회를 추가하더라도 동시 요청은 둘 다 조회를 통과할 수 있으므로 최종 판정은 DB 제약에 맡긴다.

다만 이 제약에는 앞서 정한 재주문 금지 정책이 들어 있다. 취소·만료된 주문도 남아 있기 때문이다. 재구매를 허용하는 서비스에 적용하려면 구매 자격과 주문 이력을 어떻게 관리할지 다시 정해야 한다.

JPQL 벌크 UPDATE를 쓸 때는 영속성 컨텍스트도 주의했다. DB의 수량을 바꿔도 JPA가 이미 관리 중인 엔티티 값이 자동으로 갱신되지는 않는다. 같은 트랜잭션에서 먼저 읽은 객체를 계속 사용한다면 최신 값인지 확인해야 한다. 이 구현에서는 상태 변경 성공 여부를 UPDATE의 영향받은 행 수로 판단했다.

## 재고를 돌려줄 권한도 UPDATE 결과로 판단했다

주문 생성 다음에는 예약 만료를 구현했다. 기한이 지난 `PENDING` 주문을 `EXPIRED`로 바꾸고 재고를 한 개 돌려주면 된다.

여기서도 중복 실행을 생각해야 했다. 작업자 두 개가 같은 `PENDING` 주문을 읽고 각자 재고를 반환하면 수량이 두 개 늘어난다. 서비스의 `if`로 상태를 검사하는 것만으로는 이 경쟁을 막을 수 없다.

상태 변경 조건을 DB에 넣었다. 아래 SQL은 실제 Repository의 만료 조건을 읽기 쉽게 풀어 쓴 것이다.

```sql
UPDATE orders
SET status = 'EXPIRED'
WHERE id = :orderId
  AND status = 'PENDING'
  AND expires_at <= :now;
```

같은 트랜잭션에서 이 UPDATE가 한 행을 바꾼 경우에만 재고를 반환한다.

```java
int expired = orderRepository.updateStatus(orderId, OrderStatus.EXPIRED, now);
if (expired == 1) {
    restoreStock(order.getEventId());
}
```

이미 다른 작업자가 만료시켰다면 변경된 행은 0개다. 그 요청은 재고를 건드리지 않는다. 재고 반환 자체에 실패하면 예외를 던져 주문 상태 변경도 롤백한다.

기한의 경계는 만료가 `expiresAt <= now`, 주문 확정이 `expiresAt > now`가 되도록 맞췄다. 정확히 만료 시각인 주문도 어느 쪽에서 처리할지 정해 둔 셈이다.

최종 결제 실패에도 같은 규칙을 적용했다. 결제 상태를 `FAILED`로 기록하고 `PENDING` 주문만 `CANCELLED`로 바꾼 뒤, 그 변경에 성공했을 때 재고를 반환한다. 이미 만료·취소된 주문은 다시 반환하지 않는다.

이때 만료 쿼리를 재사용하면 안 된다. 최종 실패는 기한 전에도 발생하므로 취소 조건에는 만료 시각이 들어가지 않는다.

## 응답을 못 받았다는 이유만으로 결제 실패를 기록할 수 없었다

결제에서 다룬 첫 장애는 승인 뒤 타임아웃이다.

```text
우리 서버 → 결제사: 결제 요청
결제사: 승인 완료
결제사 → 우리 서버: 응답이 지연되거나 유실
우리 서버: 타임아웃 발생
```

우리 서버에서는 예외가 발생했지만 결제사에는 승인된 거래가 있다. 이때 실패로 기록하면 돈을 받았는데 주문은 취소된 상태가 될 수 있다. 새 멱등성 키로 다시 결제하면 별도 승인이 생길 위험도 있다.

결제 상태를 `PENDING`, `UNKNOWN`, `SUCCEEDED`, `FAILED`로 나눴다. `UNKNOWN`은 최종 결과를 확인하지 못한 상태다. 타임아웃이 나면 이 상태를 기록하고, 그 이유만으로 주문을 취소하거나 재고를 반환하지 않는다. 예약 기한이 끝나면 별도의 만료 흐름이 재고를 돌려준다.

결과를 확인할 때는 처음 결제 요청에 사용한 멱등성 키를 그대로 쓴다. 같은 요청을 구분할 키는 결제 시도를 만들 때 저장해 둔다. 성공이 확인되면 성공 처리로, 최종 실패가 확인되면 실패 처리로 보낸다. 확인되지 않으면 재조회 대상으로 남긴다.

가짜 결제사에는 `TIMEOUT_AFTER_APPROVAL` 시나리오를 넣었다. 승인 결과를 저장한 다음 예외를 던져 내부 결제는 `UNKNOWN`, 결제사 거래는 `SUCCEEDED`인 상황을 만든다. 같은 키로 재요청하면 새 승인 대신 저장된 결과를 반환한다. 같은 키에 다른 주문이나 금액을 넣으면 오류로 처리한다.

조회에서 거래를 찾지 못한 경우도 `UNKNOWN`으로 뒀다. 찾지 못했다는 사실만으로 최종 실패를 확정하지 않기 위해서다. 실제 연동에서는 결제사의 상태 정의와 조회 지연, 키 보존 기간을 확인해야 한다. 이번 가짜 결제사의 동작을 모든 결제사의 계약으로 일반화할 수는 없다.

## 외부 호출을 기다리는 동안 DB 트랜잭션은 끝내 뒀다

결제 요청을 주문 트랜잭션 안에 넣으면 응답을 기다리는 동안 DB 커넥션이나 잠금을 오래 유지할 수 있다. DB를 롤백한다고 이미 끝난 외부 승인까지 취소되는 것도 아니다.

요청 준비와 결과 반영을 나누고, 그 사이에 외부 호출을 뒀다.

```text
DB 트랜잭션: 결제 상태 확인, 요청 DTO 준비 → 커밋
트랜잭션 밖: 결제 API 호출
새 DB 트랜잭션: 결과 반영 → 커밋
```

외부 호출은 `PaymentRequestService`, 짧은 DB 작업은 `PaymentAttemptTransactions`에서 담당한다. 별도 Bean으로 나눈 이유는 트랜잭션 프록시를 거치게 하려는 것이다. 기본 프록시 방식에서는 같은 객체 안에서 `this`로 `@Transactional` 메서드를 호출해도 해당 선언이 적용되지 않는다. [Spring 트랜잭션 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)에 설명된 동작이다.

아래는 요청 가능 여부를 판단하는 분기를 생략한 코드다.

```java
@Transactional(propagation = Propagation.NEVER)
public void requestPayment(Long paymentAttemptId) {
    var preparation = paymentTransactions.prepareRequest(paymentAttemptId);

    // 실제 코드에서는 SKIP, QUERY 분기를 먼저 처리한다.
    PaymentGateway.PaymentResult result;
    try {
        result = paymentGateway.pay(preparation.request());
    } catch (PaymentGatewayTimeoutException exception) {
        paymentTransactions.markUnknown(paymentAttemptId);
        return;
    }

    applyResult(paymentAttemptId, result);
}
```

`Propagation.NEVER`는 기존 트랜잭션이 있는 호출을 오류로 드러낸다. 트랜잭션을 잠시 중단하는 옵션과는 다르다. [Spring의 전파 옵션 정의](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Propagation.html)를 확인하고 외부 호출 경계에 사용했다.

`catch` 범위도 외부 호출에 한정했다. 승인 후 `applyResult()`에서 DB 저장이 실패한 오류까지 결제 실패로 기록하면 안 된다. 그 경우에는 원래 거래를 조회해 결과 반영을 재시도해야 한다. `markUnknown()` 역시 이미 성공·실패가 확정된 결제를 이전 상태로 되돌리지 않게 했다.

## 만료된 주문에서 승인을 확인하면 환불한다

처음에는 만료 뒤 성공을 확인했을 때 결제 상태만 성공으로 바꾸면 될 것 같았다. 하지만 예약 해제와 결제 승인은 각각 처리할 일이 남는다.

만료 처리에서 재고를 반환했다면 그 재고를 다른 사용자가 이미 구매했을 수도 있다. 늦게 온 승인으로 원래 주문을 확정하면 재고를 초과 판매할 위험이 있다. 이번 정책에서는 주문을 만료 상태로 유지하고 환불한다.

| 성공 결과를 반영할 때의 주문 | 처리 |
| --- | --- |
| `PENDING`, 기한 전 | 결제 승인 기록, 주문 확정 |
| `PENDING`, 기한 도달 또는 경과 | 승인 기록, 주문 만료, 재고 반환, 환불 요청 저장 |
| `EXPIRED` 또는 `CANCELLED` | 승인 기록, 환불 요청 저장. 재고는 추가 반환하지 않음 |
| 이미 같은 승인을 처리함 | 중복 반영 종료 |

만료 스케줄러가 아직 실행되지 않았어도 기한은 검사한다. 성공 처리에서 기한이 지났다고 판단하면 직접 주문을 만료시키고 재고를 반환한다. 스케줄러가 늦었다는 이유로 기한 지난 주문을 확정하지 않도록 했다.

결제 성공·실패·결과 불명 기록은 주문을 먼저 잠그고 결제 시도를 다음에 잠그는 순서로 맞췄다. 결제 결과를 반영할 때 `PESSIMISTIC_WRITE`로 같은 주문의 처리를 직렬화한다. 만료 작업과의 경쟁은 주문 행의 조건부 UPDATE와 잠금으로 처리한다.

잠금을 얻기 전에는 결제 엔티티 전체 대신 연결된 주문 ID만 조회했다. 잠금 대기 전에 엔티티를 관리 대상으로 올려 두면 잠금을 얻은 뒤에도 메모리에 이전 상태가 남아 있을 수 있어서다.

승인 사실, 필요한 주문 만료와 재고 반환, 환불 요청과 환불 작업은 같은 트랜잭션에 저장한다. 실제 환불 API는 커밋 뒤 별도 작업자가 호출한다. 중간에 DB 저장이 실패하면 이 변경들도 함께 롤백된다.

환불이 끝나도 결제 상태는 `SUCCEEDED`로 유지한다. 승인됐던 사실을 남기고 환불 결과는 별도 레코드에 기록한다. 주문 만료와 결제 승인, 환불 완료를 각각 확인할 수 있게 한 것이다.

성공과 최종 실패 통지가 충돌하면 나중 결과로 덮어쓰지 않는다. 이번 구현에서는 오류로 드러내고 원래 거래를 확인할 대상으로 남긴다.

## Kafka에 보내기 전에 발행할 이벤트를 저장했다

결제를 비동기로 처리할 때는 DB 커밋과 메시지 발행 사이를 살폈다.

```text
주문 저장과 재고 예약 커밋
→ Kafka 발행 전 애플리케이션 종료
→ 결제 요청을 전달하지 못함
```

Outbox에는 전달할 이벤트를 저장한다. 주문 생성 트랜잭션에서 주문·재고 예약·결제 시도와 함께 Outbox 이벤트와 발행 작업을 저장했다. 커밋된 이벤트는 작업자가 읽어 전달한다.

발행 성공 뒤에도 실패할 지점이 있다.

```text
Kafka 발행 성공
→ Outbox 완료 표시 전 종료
→ 재시작 후 같은 이벤트 재발행
```

Outbox를 넣었다고 중복 전달이 없어지지는 않는다. 이벤트 ID를 유지한 채 재발행하고 소비자가 중복을 판정하도록 했다.

소비자는 Inbox에 수신한 이벤트 ID를 기록한다. 수신 기록만 저장하고 결제를 호출하면 또 다른 빈틈이 생긴다. 수신 기록 커밋 직후 종료되면 재전달된 메시지는 중복으로 걸러지는데, 결제 작업은 실행되지 않았을 수 있다.

그래서 Inbox 수신 기록과 결제 작업을 같은 DB 트랜잭션에 저장했다. 소비자는 나중에 다시 실행할 수 있는 작업까지 남긴다. 이 DB 트랜잭션이 커밋된 뒤 리스너가 반환되고 Kafka 오프셋을 커밋하도록 구성했다.

```text
주문 트랜잭션
  주문 + 재고 예약 + 결제 시도 + Outbox + 발행 작업
      ↓
발행 작업자
  로컬 전달 또는 Kafka 발행
      ↓
소비자 트랜잭션
  Inbox 수신 기록 + 결제 작업
      ↓
결제 작업자
  트랜잭션 밖에서 결제 요청·조회, 별도 트랜잭션으로 결과 반영
```

중복을 막는 키의 범위도 나눴다.

| 키 | 막으려는 중복 |
| --- | --- |
| `(user_id, event_id)` | 같은 사용자의 같은 이벤트 주문 |
| 이벤트 ID | 같은 메시지의 재전달 |
| `payment:{attemptId}` | 같은 결제 시도의 작업 중복 생성 |
| 결제 멱등성 키 | 외부 승인 중복 |
| 환불 멱등성 키 | 외부 환불 중복 |

서로 다른 이벤트 ID가 같은 결제 시도를 가리켜도 결제 작업은 하나만 만든다. 이벤트 ID 유니크 제약만으로 결제 중복까지 막을 수 있다고 가정하지 않았다.

Kafka 프로듀서에는 `acks=all`과 멱등 전송을 설정했다. 하지만 애플리케이션 재시작 후 다시 보내는 업무 이벤트와 외부 결제까지 한 번만 실행하도록 보장하지는 않는다. [Kafka 설계 문서](https://kafka.apache.org/41/design/design/)의 전달 보장 범위를 확인하고 DB 중복 판정과 결제사 멱등성 키를 함께 유지했다.

## 작업자를 다시 실행할 수 있게 남긴 기록

Outbox·결제·환불 작업은 `work_items`에 저장한다. `READY`에서 작업자가 선점하면 `RUNNING`, 끝나면 `DONE`이 된다. 반복 오류나 최종 환불 실패는 `REVIEW`에 남긴다.

선점 유효 시간은 30초이고 선점할 때마다 새 토큰을 만든다. 작업자가 종료되면 기한이 지난 작업을 다른 작업자가 이어받을 수 있다. 완료나 재시도를 기록할 때는 현재 선점 토큰과 일치하는지 검사한다.

예를 들어 A가 멈춘 사이 B가 같은 작업을 이어받았다고 하자. 뒤늦게 돌아온 A는 예전 토큰으로 완료 상태를 기록할 수 없다. 다만 이미 보낸 외부 요청까지 중단되지는 않는다. 이 때문에 선점 토큰을 쓰더라도 외부 결제와 환불에는 같은 멱등성 키가 필요하다.

일시적인 오류는 간격을 늘려 재시도하고 10회 소진하면 오류와 함께 `REVIEW`로 남긴다. 실패 작업을 삭제하거나 완료로 표시하지 않는다. 검토 후 재처리할 기록을 보관한다.

환불도 별도 멱등성 키로 조회·요청하고 결과를 기록한다. 환불 완료 후 응답을 받지 못했거나 작업자가 종료된 경우, 같은 키로 재처리해 중복 환불을 막는 흐름을 확인했다.

## 테스트에서 확인한 것과 아직 확인하지 않은 것

2026년 10월 19일 전체 빌드 기준 테스트 64개가 통과했다. 실패와 건너뛴 테스트는 없었다. 다음 상황들을 중심으로 작성했다.

- 마지막 재고 한 개에 요청 8개가 동시에 들어올 때 한 주문만 성공하는지
- 중복 주문과 재고 차감 실패에서 주문 생성이 롤백되는지
- 만료·성공·실패 처리의 중복과 경쟁에서 재고를 두 번 반환하지 않는지
- 승인 뒤 타임아웃이 `UNKNOWN`으로 남고 원래 키 조회로 결과를 반영하는지
- 만료 뒤 승인 확인이 주문 확정 대신 환불 요청으로 이어지는지
- 메시지 재전달과 오프셋 커밋 전 오류에서 결제 작업이 중복 생성되지 않는지
- 작업 선점 만료 후 인계, 이전 토큰 거부, 재시작 후 미완료 작업 복구가 되는지

Kafka 테스트는 내장 KRaft 브로커로 발행과 소비를 검증했다. Docker Compose 설정은 준비했지만 컨테이너를 띄운 실행까지 검증한 결과는 아니다.

재시작 테스트는 파일 H2와 별도로 저장한 가짜 결제사 장부를 사용했다. Spring 애플리케이션 컨텍스트를 닫고 다시 열어, 남아 있는 승인 결과를 조회하고 미완료 작업을 이어 가는 흐름을 확인했다.

H2의 MySQL 모드를 사용했다고 MySQL의 잠금·격리 수준·성능까지 검증한 것은 아니다. [H2 호환 모드 문서](https://h2database.com/html/features.html)에서 지원 범위를 확인하고, 실제 MySQL 경쟁 조건은 별도 실험으로 남겼다. 요청 8개의 동시성 테스트도 대규모 부하 검증과는 범위가 다르다.

가짜 결제사의 메모리 동기화와 파일 장부는 단일 JVM 실습용이다. 여러 애플리케이션 인스턴스가 독립된 실제 결제사와 통신하는 환경까지 재현하지 않는다. Kafka 소비 오류도 현재는 무한 재시도로 남겨 두므로 잘못된 메시지가 파티션 처리를 막을 수 있다. 운영에 적용한다면 오류 메시지 격리와 알림, 수동 확인·재처리 절차를 구체화해야 한다.

## 다시 재현해 볼 때

기본 실행에서는 자동 작업자가 꺼져 있다. 주문을 만들고 H2에서 `payment_attempts.id`를 확인한 뒤 아래 순서로 요청하면 승인 후 타임아웃과 재조회를 볼 수 있다. `{attemptId}`는 주문 ID가 아닌 결제 시도 ID다.

```powershell
.\gradlew.bat bootRun
```

```http
POST http://localhost:8080/api/practice/payments/{attemptId}/scenario?scenario=TIMEOUT_AFTER_APPROVAL

POST http://localhost:8080/api/practice/payments/{attemptId}/request

POST http://localhost:8080/api/practice/payments/{attemptId}/reconcile
```

만료 후 환불을 보려면 새 사용자로 주문을 만들고 같은 타임아웃을 발생시킨다. 그 주문의 `expires_at`을 과거로 바꾼 뒤 만료 작업을 실행하고 결제 결과를 조회한다. 환불 작업은 `work/run`으로 실행한다. 새로 생긴 후속 작업은 다음 실행에서 처리할 수 있다.

```http
POST http://localhost:8080/api/practice/expiry/run

POST http://localhost:8080/api/practice/payments/{attemptId}/reconcile

POST http://localhost:8080/api/practice/work/run
```

기본 메모리 DB는 종료하면 사라진다. 자동 처리와 재시작 복구를 실습하려면 아래 프로필을 사용한다.

```powershell
.\gradlew.bat bootRun --args='--spring.profiles.active=persistent,auto'
```

재고 차감에서 시작했지만, 구현하면서 더 자주 확인한 것은 중간에 멈췄을 때 남는 데이터였다. 승인 뒤 응답을 잃어도 원래 거래를 찾을 키가 있는지, 메시지 수신 기록 뒤 실행할 작업도 남았는지, 재고를 이미 반환했는지 확인할 상태가 있는지를 살폈다.

다시 코드를 볼 때도 외부 호출 직후나 DB 커밋 직전에 실행이 멈췄다고 가정해 보려고 한다. 그다음 실행이 무엇을 읽고 어디서 이어 갈지 설명할 수 있어야 중복 요청과 재시작을 다룰 수 있었다.
